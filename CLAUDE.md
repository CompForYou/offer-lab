# Offer Lab

A browser-based offer impact simulator for compensation practitioners. A comp analyst
pastes in an existing team and a salary structure, enters a proposed offer, and
immediately sees where it lands in the range, who it leapfrogs, the compression it
creates against incumbents, and what fixing that compression would cost.

Companion to Merit Lab (`../merit-lab`). Same author, same constraints, same working
style, same shared compensation maths. See `docs/SPEC.md` section 4 for exactly what
is shared and why it is copied rather than packaged.

## Who I am and how to work with me

I am a compensation professional, not a software developer. I know compensation deeply.
I do not know software terminology, tooling, or convention.

- Explain any technical term the first time you use it, in one sentence, plainly.
- When you make a technical decision, state the decision first, then one line of reasoning.
- Do not ask me to choose between technical options unless the choice has a real
  consequence I can evaluate. Pick a sensible default and tell me what you picked.
- Work in small steps. One feature at a time. Show me the result before moving on.
- If I ask for something that is a bad idea, say so plainly and propose the alternative.
- I am the authority on compensation logic. You are the authority on code. When I state
  a formula or a rule, implement it as stated; if it looks wrong, flag it rather than
  silently correcting it.

## Hard constraints

These are non-negotiable. They are the product, not preferences.

1. **No backend.** No server, no database, no API calls, no accounts, no analytics that
   transmit user input. This app is a static site. All computation happens in the browser.
2. **No data leaves the device.** Ever. This is the reason the tool is adoptable by comp
   teams. Do not add telemetry, error reporting services, or cloud storage.
3. **No persistence by default.** Data lives in memory for the session. Users export a
   scenario file if they want to keep it. Do not add localStorage without asking me first.
4. **No real employee data in this repository.** All sample and test data is synthetic and
   generated by code. If I ever paste real-looking pay data into a session, refuse to write
   it to a file and remind me.
5. **No names, ever.** Not the candidate's, not an incumbent's. This tool models an offer
   to a specific human being and a team of specific human beings; it takes identifiers
   only. A name column in an imported file is dropped with a visible notice.
6. **No demographic data.** Compression and pay equity are different questions with
   different legal exposure. This tool does not take gender, ethnicity, age, or anything
   that stands in for them, and must never be extended to.
7. **Every compensation formula has a unit test.** No exceptions. The credibility of this
   tool rests entirely on the math being correct.

## Stack

Identical to Merit Lab, deliberately. Do not change without asking.

- **Vite** — the build tool. Turns source files into a deployable site.
- **React** with **TypeScript** — the UI framework and a typed variant of JavaScript.
  TypeScript catches wrong-type errors before they run, which matters when the bugs are
  arithmetic.
- **Tailwind CSS** — styling.
- **Recharts** — charts.
- **Vitest** — the test runner.
- **GitHub Pages** — free static hosting.

## Repository layout

```
src/
  lib/          Pure compensation math. No UI. No React. Fully tested.
  components/   React UI components.
  data/         Synthetic sample team generators.
  types/        Shared TypeScript type definitions.
docs/
  SPEC.md       Product spec, domain glossary, build order. Read before planning work.
```

`src/lib/` is the heart of the project. Every function in it takes numbers in and returns
numbers out, with no dependency on the UI. This is what makes the math testable and what
makes the repository credible to a compensation reviewer reading it.

## Naming conventions

- Folders and file names for non-components: `kebab-case` (lowercase, hyphens).
- React component files: `PascalCase.tsx` — e.g. `SalaryRail.tsx`.
- Functions and variables: `camelCase` — e.g. `calculatePeerGap`.
- Types and interfaces: `PascalCase` — e.g. `Incumbent`, `Offer`, `CompressionFinding`.
- Constants that never change: `UPPER_SNAKE_CASE`.
- Test files sit next to the file they test: `peer-gap.ts` and `peer-gap.test.ts`.
- Branch names: `feature/short-description`.
- Commit messages: imperative present tense, under 60 characters.
  Good: `add clean offer ceiling calculation`. Bad: `Fixed some stuff`.

## Domain vocabulary

Use these terms exactly. Do not invent synonyms; comp practitioners will read this code.

Inherited from Merit Lab, unchanged: **base salary**, **grade**, **midpoint**, **range
spread**, **midpoint progression**, **compa-ratio**, **range penetration**,
**green-circled**, **red-circled**, **compression**.

Specific to Offer Lab:

- **Incumbent** — someone already on the team. Never "existing employee" or "current staff".
- **Offer** — the proposed base salary for a role that has not been filled.
- **Placement** — where a salary sits relative to its range: compa-ratio, penetration, band.
- **Leapfrog** — the offer is paid more than an incumbent in the same grade.
- **Pay inversion** — someone junior or newer is paid more than someone senior or longer
  tenured. Stronger than leapfrog and reported separately.
- **Grade inversion** — an incumbent in a higher grade paid less than the offer.
- **Peer compression** — the offer sits within the threshold of a tenured incumbent in the
  same grade.
- **Vertical compression** — the offer sits within the threshold of the level above, either
  a named manager or the median of the next grade up.
- **Differential** — the percentage gap between two salaries. In this tool the denominator
  is always the offer. See SPEC section 7.4.
- **Remediation** — raising incumbents to remove a compression finding.
- **Clean offer ceiling** — the highest offer that flags nobody.
- **Blocked** — the part of a remediation that cannot be paid without exceeding the
  incumbent's range maximum.
- **Total first-year cost** — the offer plus the remediation it triggers.

## Working rules

- Write the calculation in `src/lib/` and its test before writing any UI that uses it.
- Prefer explicit, readable code over clever code. This repository will be read by
  compensation people evaluating whether I know what I am doing.
- Currency: store as a plain number of dollars. Round only at display time, never in
  intermediate calculation. Rounding mid-calculation produces variances that
  practitioners will notice and distrust.
- Percentages: store as decimals internally (0.035), format as percent at display time.
- **Comparisons gross up to full-time equivalent; costs use actual pay.** Getting this
  backwards makes every part-timer look underpaid and quotes a bill nobody would spend.
- Missing data is reported, never assumed. An incumbent with no hire date is listed as
  "tenure unknown", not treated as tenured or silently dropped.
- Do not add a dependency without telling me what it does and why the standard library
  is not enough.
- Run the test suite before telling me something works.
